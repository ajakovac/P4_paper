F0_SINGLE_RELATION_COMPLETION

derives_F0(T,U,R,X,O) :-
    and(task_unknown(T,X),
        unknown_location(X,U,I),
        scalar_relation_candidate(U,I,R,O))

F0 derives values only from represented R-edges adjacent to the unknown
position.  If both semantic neighbours are known, the candidate must satisfy
both edge conditions.  If only one semantic neighbour is known, that side is
used.  If neither side is known, F0 derives no candidate.

F0 does not enumerate context members as candidate values.  The complete
same-relation-on-successive-positions constraint is checked later by
satisfies_constraints.

F3_STRUCTURAL_ALL_ONCE_LIFTING

derives_F3(T,U,X,P) :-
    and(task_unknown(T,X),
        unknown_location(X,U,I),
        unknown_type(X,Pair(tau1,tau2)),
        target_role_residual(T,U,1,D1,O1),
        target_role_residual(T,U,2,D2,O2),
        pair(P,O1,O2),
        otype(P,Pair(tau1,tau2)))

F3 performs canonical structural lifting.  Pair syntax supplies only two stable
roles.  F3 projects those roles, requires at least two complete reference
streams of the same represented item type, infers one common finite domain per
role from those complete streams, verifies that each complete reference uses
each role-domain value exactly once, derives the unique missing value in each
role of the incomplete target stream, and recombines those two values.

F3 does not enumerate arbitrary decompositions or arbitrary candidate values.
It also does not require task-declared component contexts or ALL_ONCE
constraints.  The successful episode may therefore support learning a reusable
two-role componentwise ALL_ONCE lifting schema.

The final pair must still be explicitly representable by pair(P,O1,O2); this is
a representation condition, not a pre-supplied solution schema.

F4_PAIR_COMPONENT_RELATION_COMPLETION

derives_F4(T,U,X,P) :-
    and(task_unknown(T,X),
        unknown_location(X,U,I),
        unknown_type(X,Pair(tau1,tau2)),
        task_component_relation(T,U,1,R1),
        task_component_relation(T,U,2,R2),
        component_relation_candidate(U,I,1,R1,O1),
        component_relation_candidate(U,I,2,R2,O2),
        pair(P,O1,O2),
        otype(P,Pair(tau1,tau2)))

F4 applies represented component relations only after the visible KS contains
a reusable two-role structural-lifting schema learned from an earlier F3
episode.  It then applies the represented relation of each component at the
unknown semantic position, using POSITION_NEXT rather than identifier spelling
or source order, and recombines the two derived components.

If both semantic neighbours of a component are known, the component candidate
must satisfy both adjacency conditions.  Complete component-relation
constraints are checked later by satisfies_constraints.

F1 is a controlled application of an explicitly represented reusable object K.
K must have proposal-source permission, an input type matching U, and exactly
one executable runtime mode.

For a stored scalar single-relation rule/schema, F1 requires exactly one
associated relation and delegates binding derivation to the F0 semantics.

For a stored structural ALL_ONCE-lifting schema, F1 delegates to F3.

For a stored structural component-relation schema, F1 delegates to F4.

For stored_componentwise_reuse, F1 permits exactly the mixed two-component
cases used by the restricted demonstration: one component is ALL_ONCE and the
other is relation constrained.  Each component is derived by its corresponding
deterministic mechanism, and the result must resolve to an explicitly
represented pair object.

F1 does not synthesize a new procedure, relation, rule, schema, pair object, or
context member.

RESTRICTED_FAMILY_CLOSURE

The operational meanings of F0, F1, F3, and F4 are completely specified by
this P0 block for the restricted T1--T5 experiment.  No external executable
design document may add candidate-generation semantics.

F2 remains outside the frozen restricted profile and has no runtime derivation
semantics here.

All finite alternatives produced by the definitions above enter the common
candidate/evaluation/selection pipeline.  Deterministic output order is imposed
by the selection block, not by incidental parser order.

STREAM_SCOPED_COMPONENT_SEMANTICS

Every F4 and mixed F1 lookup of an explicitly represented component context,
ALL_ONCE constraint, or component relation is performed for the same stream U
being completed.  F3 does not read task-declared component metadata: its role
domains are inferred only from complete reference streams of the current task.
No component metadata may leak across U2, U3, U4 or any other simultaneous
task inputs.

PROFILE_SERIALIZATION_CONTRACT

A surviving candidate is serialized as one M7 proposal object for task T,
with one assignment of X to O and one explicit support object representing the
procedure/schema/rule application corresponding to H.

Every serialized proposal is paired with one M8 evaluation object containing
exactly the five required checks in canonical profile order.

The M7/M8 serialization is transient DP output.  Serialization does not insert
the proposal, evaluation, or support object into the persistent Knowledge
Space.

F1_REUSE_CLOSURE_POLICY

A successful F1 reuse episode does not automatically propose a new reusable
rule, schema, or procedure in the restricted T1--T5 profile.  Its use is
recorded in the raw trace and may support existing reusable knowledge.
Any later extension that proposes status changes after repeated reuse must be
specified explicitly and is not implied by P0 v0.9.

KNOWLEDGE_PROPOSAL_BUNDLE_CONSTRUCTION

For every selected survivor supported by F0, F3, or F4, DP emits exactly two
transient reusable-knowledge descriptions:

1. one exact rule description with status verified;
2. one reusable schema description with status supported.

For F0, both descriptions preserve the explicitly selected associated
relation R.

For F3 and F4, the reusable schema preserves the procedure family and the
derived input/output types but does not preserve task-local identifiers.
An F3 reusable schema additionally records schema_structure_arity(S,2) and
schema_component_mode(S,all_once).  These facts are learned output of the
successful structural-lifting episode, not task input.

No persistent identifier is created by DP.  Persistent identifiers are
assigned deterministically by KSU according to KSU_SPEC_v03.

The proposer does not create a permanent reusable object merely because a
knowledge description is emitted.  Persistent rule/schema creation and
admission belong exclusively to KSU.

RAW_TRACE_REQUIREMENTS

Every DP invocation emits exactly one transient raw_trace_serial RS.

raw_trace_task(RS,T) names the current task.

N is a positive integer execution index local to RS.
For one RS, each N occurs at most once.
The sequence is ordered by increasing N and records actual deterministic
execution order.

A raw trace serial may refer only to objects, reusable rules, schemas,
procedures, hypotheses, candidate bindings, checks, results, and outcomes
that were actually read, applied, derived, evaluated, selected, rejected,
or produced during the current invocation.

The raw trace serial is not a Knowledge-Space object, not a permanent trace
node, and not itself inserted into persistent memory by DP.

The raw trace serial is an execution record.  It must not contain inferred
future KS structure or accepted reusable objects.

The proposer receives one current task and one externally prepared visible KS
snapshot.  It is not given the future T1--T5 curriculum as a batch and it does
not carry task-result memory internally.

The procedure families F0, F1, F3, and F4 are fixed implementation mechanisms,
but their applicability is not equivalent to pre-supplying a learned schema.
In particular, Pair is only representation grammar; F3 must infer the
componentwise ALL_ONCE regularity from complete exemplars, and F4 is gated by
a reusable two-role structural-lifting schema admitted after such an episode.

What may change between invocations is the visible KS produced by KSU from the
preceding task's complete DP output bundle.

The P0 specification is deterministic runtime code/configuration.  It is not
concatenated with the task as an LLM prompt and it supplies no hidden task
facts beyond the explicit current task, visible KS, and fixed P0 code.

KSU behavior, admission modes, persistent identifier assignment, permanent
trace materialization, and KS commit semantics are defined by KSU_SPEC_v03.
